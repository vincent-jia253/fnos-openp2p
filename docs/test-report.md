## 四、重点评审

### ① B6 —— 由「未验证」改判「已验证」（**同意**）

- **缺陷本体**：`fix_binary_arch`/`detect_cpucore` 对 `uname -m=armv8l` **无映射 → 选错文件**（32 位 ARM 用户态 + 64 位内核设备装不上）。
- **修复确在交付包内**（qa 解包复核）：`cmd/common:185` `armv8l) echo "armv7"`；同段另覆盖 `armv7hl/armv7a/armv6l`。
- **动态证据成立**（`exec-E.log`）：
  - TC-08d 用 **PATH 前置 shim** mock `uname -m`，逐条断言落盘文件内容：`armv8l/armv7hl/armv7a/armv7l/armv6l→armv7`、`aarch64/arm64→aarch64`、`amd64/x86_64→x86_64`、`i686/i386→i386`、`riscv64→rc=1+「不支持的系统架构」` —— **13/13 PASS**。
  - B6 专项：`armv8l` 设备日志含「架构 armv7」、落盘权限 755 —— 2/2 PASS。
  - TC-08e 真二进制佐证：包内 `openp2p_armv7`（md5 `4afa700df8b0612696a00ab5161b68a0`，qa 复算一致）经 `qemu-arm-static` 实测输出 `3.25.11`。
- **qa 复核实现**：`APPDEST="${TRIM_APPDEST:-...}"`、`PAYLOAD_BIN="${APPDEST}/bin"`、`detect_cpucore` 用裸 `uname -m`（src 未覆写 PATH）→ shim 生效路径成立；断言直接检查 `$DATA/openp2p` 的**桩内容**（`9.9.9-<arch>`），故准确指向「选了哪个架构文件」。
- **裁定**：B6 缺陷本体（选错文件）已被**针对性动态验证**，且配套二进制的可执行性由 TC-08e 佐证 → **改判「已验证」**。
- **残余（已知、非阻塞）**：验证经「脚本桩隔离 + qemu」完成，**无原生 armv8l 真机**执行；对 B6 的缺陷定位（架构选择逻辑）已充分，保留为已知残余。

#### 关于 `mock 自检: armv8l (期望 armv8l)` 行是否足以排除「脚手架假象」

- **单看该行：不足以**。它是 case_m **之外**的一条独立探测，只能证明「此刻 PATH shim 可解析为 armv8l」，**不能直接证明** case_m 内 `install_callback` 运行时 shim 仍在 PATH 生效。
- **但整条证据链成立**，理由有二，且不依赖该行：
  1. **自证性**：若 shim 在 case_m 内未生效，`uname -m` 全部回落真实 `x86_64`，则 `armv8l/armv7hl/…` 各条**必然 FAIL**（落盘 `9.9.9-x86_64`），恰为编排者描述的 v1「12 条 FAIL 且全落 x86_64」症状。现这些条 **PASS**，即证明 shim 在 case_m 内**确实生效**。
  2. **独立佐证**：TC-08e 用**真二进制**（非桩）经 qemu 实测可执行，与桩断言相互独立。
- **裁定**：该自检行是**有效绊线（tripwire）但非充分证明**；本次 E 的**证据链成立**，成立依据是「负向证据 + 自证性 PASS 模式 + TC-08e 独立佐证」的合力。

### ② i386 —— 维持「环境受限 · 非缺陷 · 未验证」（**同意**）

- `exec-D.log`：i386 `-v` 崩溃 `fatal error: unexpected signal during runtime execution`；TC-08c 对照**官方 Go 386 工具链**在同一 `qemu-i386` 下**同样崩溃**（`[signal SIGSEGV …]`）。
- i386 二进制头部/大小/Go BuildID/`go1.20.14` 与另三架构**同源同构**，非截断/损坏；`file` 输出结构完好的静态 ELF。
- **裁定**：`该 FAIL 不计产物缺陷`（崩溃点与官方 Go 386 在**同一 qemu-i386** 下完全一致 → 属 qemu 对 Go 二进制模拟局限）。但**无任何原生 i386 执行**，严格为「**测试环境局限导致的未验证**」，**不能记为已验证可用**。维持上一轮「环境受限·非缺陷」。
- **非发布阻塞的附加理由**：本包 `install_callback` 内置候选自检（`$cand -v`）；即便 i386 构建真有缺陷，在**原生 i386 设备**上自检会失败并 **fail-fast rc=1**，不会静默装入一个跑不起来的应用（风险被显式化）。

### ③ T2 —— 闭环，且**同意「改文档而非改实现」**

- `api.md` §4 已修订：明确 `install_callback` 在「无匹配架构且无可用二进制」「候选自检失败」场景**有意 rc=1 并中止安装**（fail-fast）；并注明「载荷无匹配架构但**数据目录已有可用二进制**」走**沿用**路径返回 **0**。
- **qa 复核实现**（解包交付包 `cmd/common`）：`fix_binary_arch` 中 `core 为空` / `src 不存在且无旧二进制` / `cp 失败` / **候选 `-v` 自检失败** / `mv 失败` → 均 `return 1`；`src 不存在但有旧二进制` → 沿用 `return 0`。**与修订后契约逐分支吻合**。
- **裁定**：**同意以实现为准、修契约**。理由：① fail-fast（装一个跑不起来的应用应显式失败）是**用户可见的正确行为**；② 修订后契约与 `testcases.md` TC-07/TC-09/TC-10/TC-12 的**既有预期不冲突**（TC-10 原预期只要求「不崩溃/不空转/有错误提示/`status rc=3`」，未约束 rc=0）；③ 改文档不引入行为风险。**T2 闭环。**
